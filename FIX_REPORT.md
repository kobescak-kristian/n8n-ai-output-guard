# FIX_REPORT: claims intake workflow

```
AUTOMATION DEBUG REPORT | Q119 Fix kit: claims intake BEFORE (broken) | 2026-10-20
Status: fixed (gated runs fixkit-gated-1, -2 and -3 on commit 9107ff3 succeeded)
Confidence: confirmed

Summary: The workflow sends a claim e-mail to Claude and passes the answer straight to JSON.parse and the
claims table, with no check in between. When the AI answer is broken, the workflow either crashes or saves
a bad claim; the fix puts the AI output guard between the AI step and the table.

What failed: node "Parse JSON" (Code node, JSON.parse of the AI answer) threw an error on 26 of 89 claim
  cases in each run; the webhook answered HTTP 500 "Error in workflow". On a further 42 cases the run
  finished green but saved a row that is wrong or should not exist.
Where it started: node "Ask the AI" (1 step before the failure): its answer is used as it comes, with no
  check of the stop reason, the JSON or the claim fields.
Why: missing output check (cause type: unvalidated AI output). An AI step can return malformed JSON,
  prose ("Here is the JSON ..."), a refusal, a cut-off answer, or no text at all after an API error.
  JSON.parse throws on these; when the answer does parse, nothing checks it against the claim schema, so
  wrong fields, out-of-range values and data from a prompt injection go into the claims table.

Evidence (same numbers in all 3 gated runs; tests/results/gated-1.score.json, fix_kit; by case kind and
  the n8n error log: tests/results/fixkit-gated-evidence.json, made by tools/fixkit_evidence.py):
- BEFORE, 89 claim cases (65 visible, 24 from the sealed hold-out): 26 crashed, 31 invalid rows saved,
  11 rows saved that should not exist, 21 valid rows.
- The 26 crashes by case kind: API error 12, malformed JSON 9, empty answer or refusal 4, prompt
  injection 1.
- The 42 bad rows by case kind: invalid rows: missing or wrong fields 12, value out of range 14, other 5;
  rows that should not exist: prompt injection 8, setup error 2, refusal 1.
- n8n error log of the BEFORE workflow, 2026-10-19 23:46 to 2026-10-20 01:18 UTC: 78 error runs (26 x 3), every one
  in "Parse JSON". Most common errors: '"undefined" is not valid JSON' (39, an API error left no text),
  'Unexpected token ... "Here is th..." is not valid JSON' (6), "A 'json' property isn't an object" (6),
  'Unexpected token "```json"' (3), "Unexpected end of JSON input" (3), "Unterminated string in JSON" (3).
- AFTER, the same 89 cases: 0 crashed, 0 invalid rows, 0 rows that should not exist, 56 valid rows saved
  (21 ok, 22 ok after one retry, 13 from the fallback). 31 went to a person in the Slack review queue
  (not written to the claims table; the reviewer approves, corrects or rejects them); 2 setup errors
  returned failed with an alert.
Trace: Save claim (wrong rows) <- Claims row (copies fields, no check) <- Parse JSON (throws) <- Ask the
  AI (answer not checked: origin) <- Read e-mail (ok) <- Claim e-mail (ok).

Unknowns:
- Real client traffic: the cases are written test cases (simulated and live Claude answers), not a
  client's e-mails. The mix of failure kinds in production will differ.

Fix: one change. Replace "Ask the AI" + "Parse JSON" with:
  1. "Guard input" (Code): pass the e-mail text, the claim JSON Schema and the fallback choice.
  2. "AI output guard" (Execute Workflow): call the guard sub-workflow, which calls the same AI step,
     checks the answer, retries once, uses the fallback and sends what still fails to review.
  3. "Checked data?" (IF): status ok, ok_after_retry or fallback -> "Claims row" -> "Save claim";
     every other status -> "Not saved" (the item waits in the review queue).
Guard: every call is logged (one row per call); every item that needs a person gets a Slack review
  message; a setup failure, a fallback or an API error also raises a Slack alert; nothing reaches the claims
  table unless it passed the schema check.

Client message:
Your claims workflow trusted every answer from the AI. When the AI sent back broken or incomplete text,
the workflow either stopped or saved a wrong claim, and nobody was told. We added one check between the AI
and your claims table: it tests every answer, asks the AI once more when the answer is broken, and sends
anything still unclear to your team in Slack. In our tests on 89 sample claims, the old version crashed 26
times and saved 42 bad rows; the new version had no crashes and no bad rows.
```
